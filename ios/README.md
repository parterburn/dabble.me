# Dabble Me for iOS

Native SwiftUI companion to the email journal: Today (prompt + On This Day), the Journal timeline with List / Stats / Photos views, search with a hashtag cloud, writing and editing with rich text and photos, reminders, a Face ID lock, a home-screen widget, and on-device Apple Intelligence.

Email is still the primary way people write. Plan rules (see `ios/AppStore/metadata.md` → Decisions): everyone can sign in, read, write and delete text entries, use the on-device AI (reflections, Today's prompt, hashtag suggestions), set a writing reminder, and see Photos and the widget; photos, links, editing, search, Stats, On This Day (and its reminder) and choosing the email's days are PRO.

## Requirements

- Xcode 27+, iOS 18+ deployment target, Swift 6
- [XcodeGen](https://github.com/yonaskolb/XcodeGen): `brew install xcodegen`

## Getting started

```bash
cd ios
xcodegen generate        # creates DabbleMe.xcodeproj (gitignored; project.yml is the source of truth)
open DabbleMe.xcodeproj
```

Xcode Cloud has no project to open after cloning, so `ci_scripts/ci_post_clone.sh` installs XcodeGen and generates it there. A merge to `main` that touches the app becomes a TestFlight build, signed by Xcode Cloud, with `TestFlight/WhatToTest.en-US.txt` as its "What to Test" notes: rewrite that file with each change. The unit tests can run there as a Test action; the UI tests need the local Rails server and demo tokens.

Debug builds point at `http://localhost:3000` and Release builds at `https://dabble.me` (the `DABBLE_BASE_URL` setting in `project.yml`). To use a local server:

```bash
# from the repo root
bundle exec rails db:migrate    # or db:seed: registers the iOS OAuth client
MAIN_DOMAIN=localhost ... bundle exec puma -p 3000 -C config/puma.rb   # see AGENTS.md
```

The simulator reaches `localhost` directly. On a phone, "localhost" is the phone itself: start Puma with your Mac's Bonjour name allowed (`RAILS_DEVELOPMENT_HOSTS=<name>.local`, see `scutil --get LocalHostName`), then in a Debug build tap **Server** on the sign-in screen → **Other…** and enter `http://<name>.local:3000`. Run `bundle exec sidekiq` too if you want photos and collages to finish processing. The seeded `admin@dabble.ex` / `dabble` account is PRO.

## How sign-in works

1. The app opens `/oauth/authorize` in `ASWebAuthenticationSession`. That page is the normal dabble.me sign-in: password, passkey, or 2FA. The session shares Safari cookies, so someone already signed in on the web just taps through.
2. Doorkeeper skips the consent screen for this first-party client (`MobileApp` in `app/lib/mobile_app.rb`) and redirects to `me.dabble.app:/oauth/callback?code=…`.
3. The app exchanges the code using PKCE (public client, no secret) for an `app:journal` access token plus a refresh token, and stores both in the Keychain.
4. API calls go to `/api/v1/*` with `Authorization: Bearer …`. On a 401 the app refreshes once, and signs out if the refresh is rejected.

`app:journal` tokens can't call `/mcp`, and MCP tokens can't call `/api/v1`. App tokens survive a PRO downgrade or passkey removal, since those only gate MCP. A password, email, or 2FA change signs the app out, and so does removing "Dabble Me for iOS" under Connected Apps on `/security`.

## API

| Method | Path | Notes |
|---|---|---|
| GET | `/api/v1/me` | account, plan, `today` in the user's journal time zone |
| GET | `/api/v1/entries?page=&per=&year=&month=&photos=1&songs=1` | newest first, 20 per page by default (max 50); `photos=1` lists only entries with a photo (Journal > Photos), `songs=1` only those with a Spotify song (Journal > Playlist) |
| GET | `/api/v1/entries/:id` | full entry: `body_text` (light Markdown), `document` (editable structure or null), songs, `web_url` |
| GET | `/api/v1/entries/random` | |
| GET | `/api/v1/entries/on_this_day` | PRO |
| GET | `/api/v1/entries/:id/same_day` | The entry's calendar day in other years, earlier and later, newest first, for On This Day under an open entry: `{available, count, entries}`. PRO gets the entries; a free account only `count` (`available: false`) |
| POST | `/api/v1/entries` | PRO. `{date, document \| body, uploaded_image_keys?}`; merges into an existing entry on that day, like the web. One photo is stored as-is; 2–8 (or any added to a day with a photo) become a collage, and the entry reports `image_processing: true` from the moment the job is queued |
| PATCH | `/api/v1/entries/:id` | PRO. Any of `{document, date, remove_image, uploaded_image_keys}`. `date` moves the entry to another day. When that day has an entry the answer is `date_taken`; the app asks, then sends `merge: true`, which adds this entry to the end of that one (photo included) and returns the merged entry. `document` only when the entry's `document` is non-null; new photos join the entry's photo in a collage, or replace it with `remove_image` |
| DELETE | `/api/v1/entries/:id` | PRO |
| GET | `/api/v1/search?q=&page=` | PRO, same syntax as web search |
| GET | `/api/v1/today` | Today tab: entry, On This Day (PRO), daily prompt, `entries_this_year` and `current_streak` (both for older builds: Today now shows the journal's total, from `/me`) |
| GET | `/api/v1/entries/months` | month index for the timeline and scrubber |
| GET | `/api/v1/entries/memory_days?days=30` | PRO. Upcoming days with memories (counts only) for On This Day reminders |
| GET | `/api/v1/reminders?days=14` | (Each day also lists `entries`: all of its On This Day entries, newest year first, up to 8, or its one Rewind. The widget shows them in turn.) The entry each coming day's push reminder looks back on (On This Day for PRO, else the day's Rewind), following the account's past-entry filters, which the email shares: none with its left-out words, and with "only the past year" just last year's from the day or one from the past 12 months. Without `all` (older builds), none at all while the email's past entry is off: `{email_hour, days: [{date, kind, count, entry: {id, date, excerpt, image_url}}]}` `all=1` (what the app sends) gives the days whatever the email's past-entry switch says, with `include_past_entries` for which way that is: the push reminder and the widget have switches of their own |
| GET | `/api/v1/stats` | Journal > Stats: totals, streaks (`longest_streak_year` is the year the longest one ended in), writing days in the past year, 12 months, top hashtags (`Api::JournalStats`) |
| GET | `/api/v1/stats/days?year=2024` | PRO. One calendar year for Stats' year picker: the days with an entry and the year's top hashtags |
| GET/PATCH | `/api/v1/email_schedule` | The daily email: `{days, hour, timezone}` (Rails zone names; `time_zones` lists them with IANA ids) and its past entry: `include_past_entries`, `past_filter` (comma-separated words that leave entries out; `filtered_count` says how many) and `include_old_entries` (`has_old_entries` says whether any are over a year old). Days beyond Sunday, the filter and old entries are PRO, like the web |
| GET | `/api/v1/hashtags?days=365` | PRO. Hashtag counts for the Search tag cloud (`Api::HashtagCounts`) |
| GET/POST/PATCH/DELETE | `/api/v1/dated_hashtags(/:id)` | PRO. Dates for #tags (Settings → Manage Hashtags), `{id, tag, date}`; the list also suggests tags used lately that have no date |
| POST | `/api/v1/image_uploads` | PRO. `{photos: [{filename, content_type}]}` (max 8) → presigned S3 PUTs; the keys go to `POST /entries` |
| GET/PATCH | `/api/v1/app_settings` | Settings kept on the account, not the phone (`AccountSettings`): `entry_template` (runs as typed, `[]` for none), `entry_template_auto`, `widget_content` (a `WidgetContent` raw value). Each is null until first set; PATCH changes only what is sent. Stored encrypted (`users.app_settings`) |

**Rich text editing.** The app never parses or sends raw HTML. `Api::EntryDocument` turns stored HTML into a `document`: a list of paragraph / bullet / number / rule blocks made of text runs that may be bold, italic, underlined or linked. A list item inside another's list has a `level` (1 for the first list in), and reads and edits set in by four spaces a level. That covers what the web editor (Summernote) and email ingestion produce, including `<div>` lines from email and `<hr>` between merged replies. The app edits the document in a native text view (Bold is always in the bar, for what's typed next; with words selected, or Bold held, the bar is the formats' alone: Link on the left, with Visit and the trash beside it for a link that's there, and Bold, Italic and Underline on the right, each lit while all the selected words have it; photos, hashtags and prompts are out of the way until the selection's let go or the cursor's put somewhere else; the text's own Format menu has them too. The format buttons are the letters B, I and U in a serif and the system's link symbol, not Slab icons: they stand alone in the bar, and the set has none; typing "- ", "* " or "1. " starts a list; the bar has "+" for photos and hashtag suggestions, and link; dictation is the keyboard's own) and sends it back, and the server rebuilds clean HTML from it (`to_html`). Entries with anything the document can't represent — inline styles, blockquotes, headings, images in the text — come back with a simplified document (`simplified_from_html`: the text and what formatting it can keep) and `document_simplified: true`. The editor says so in a banner: saving rewrites the entry without that formatting, and Cancel leaves it as it was.

**Widget.** `DabbleMeWidget` (WidgetKit) reads a `WidgetSnapshot` the app writes to the `group.me.dabble.ios` App Group after each refresh: whether today is written (shown under today's date, "SAT" over "10", as the app's entries show theirs), the year's entry count (the Lock Screen's circular widget; the inline and rectangular ones have the date) and today's prompt (the personal Apple Intelligence one when there is one). Settings → Home Screen Widget (`WidgetSettingsView`, with a live preview drawn by the widget's own `TodayWidgetContent` from `Shared/`) chooses what the medium widget shows beside the date (`WidgetContent`): a prompt ("A Prompt for You", the default) or a Rewind (On This Day, else the past entry Today shows), each with or without entry previews. Without previews, Rewind is a count or a note that there's a memory; with them, it's the entry (and A Prompt for You gives way to today's own entry once it's written): a label and the start of its text, plus a small copy of its photo (saved to the App Group as `WidgetPhotos/entry-<id>.jpg`, at most 700pt wide), which fills the medium widget's right side under a few words of the entry. Only previews put entry text or photos on the widget, and the choice is the person's alone: the Face ID lock doesn't change what the widget shows. With Rewind chosen, the snapshot also carries the look back for each of the next two weeks (`upcoming`, from `/api/v1/reminders`; the entry's words and photo only with previews on), so the widget has one each morning without the app being opened first; the background refresh tops it up. A day with several entries from past years carries them all (`Day.rotation`, from the endpoint's `entries`, up to six): with previews on, they take turns on the widget through the day, sharing 6 AM to midnight equally (`WidgetSnapshot.rotationIndex`; four are four and a half hours each), each a timeline entry of its own, and a tap opens Today at the one showing. Today's comes from there too, so the filters in Settings → Reminders → Past Entries hold on every day (the words left out never show). The marks under the date are small dots. Each widget can also choose for itself on the Home Screen (touch and hold, Edit Widget: `TodayWidgetIntent`, an `AppIntentConfiguration`); left on "Same as in the App" it follows the setting. So the snapshot always holds the start of today's entry and of the look back, and a widget shows them only when its choice has previews. A tap on the date side (or the small widget) opens Today, written or not. A tap on the medium widget's right side opens Today too, scrolled to what it shows (`WidgetEntry.detailURL`, read back by `TodayFocus`): the entry looked back on (`me.dabble.app:/today/entry/<id>`), or the On This Day or Rewind title when it's a count or a note (`:/today/lookback`); today's own entry and a prompt open Today at its top. An entry Today doesn't list (the widget's pick follows the past-entry filters, and a free account's Today has no Rewind) opens in the Journal instead, as `:/entry/<id>` from an older build's widget still does. Under the date is a row of five small marks, the last five days (today's last), a filled dot when that day was written and an open ring in the same color when it wasn't (`writtenDays` in the snapshot, a few weeks' worth so the row moves on at midnight): quiet on purpose, no count and no streak. The same five dots (`LastFiveDays`, from `AppModel.lastFiveDays`) are in Today's corner before the journal's count ("20 entries", which opens Stats), and in Stats under the tiles with what they mean ("3 of the last 5 days have entries."). In Today's corner the dots show alone for someone who's written in those five days, and the count ("20 entries") otherwise; from December 15 to January 15 it's "2026 Rewind" for everyone, until it's been tapped once (a free account's Stats page then names the Rewind among what PRO has).

**Links.** A dabble.me link tapped elsewhere on the phone (Mail, Messages, Notes) opens in the app when it's one of these (universal links: `AppLink`, the `applinks:dabble.me` entitlement, and the server's `/.well-known/apple-app-site-association`, from `MobileApp::LINK_PATHS`): `/entries` (the Journal), `/today`, `/entries/new` or `/write` (the composer: until 10 AM on yesterday's entry when that's unwritten, as the web page itself does), `/entries/2026/11/13` (that day's entry, or the composer on a day without one), `/search` (the Search tab; with the web's `?search[term]=…`, that search run in it), and `/rewind` or `/rewind/2026` (Stats, where Rewind is). Every other page stays on the web. iOS only does this for links tapped outside Safari's own dabble.me pages, and learns the list when the app is installed or updated.

**Control.** `NewEntryControl` (in the widget extension, iOS 18's `ControlWidget`) is a New Entry button for Control Center, the Lock Screen and the Action button. Its icon is the "me" mark as a custom SF Symbol (`Shared/WidgetIcons.xcassets/dabble.me.symbolset`: Instrument Serif's own outlines in Apple's symbol template, Regular weight at the small and medium scales, checked with the SF Symbols app's Validate Templates). Its `NewEntryIntent` (`Shared/`, in both targets, and so in Shortcuts too) opens the app and leaves word in the App Group (`NewEntryControlRequest`, good for a minute); the app takes it when it comes forward and opens the composer as its other New Entry shortcuts do (`AppModel.requestNewEntry`: before 10 AM on yesterday if that's unwritten, otherwise today).

**Launch.** The launch screen is the Paper color; then `SplashView` types "me." in the icon's square with a blinking cursor until the journal has loaded (about 0.9 seconds at least and 2 at most; just the icon with Reduce Motion). The Face ID lock types the wordmark too and asks for Face ID at once, without waiting on the typing; its Face ID symbol tries again when tapped. With the lock on, the journal is covered by the "me" mark whenever the app isn't active (`PrivacyCover`, for the app switcher), except right after an unlock: until the app is active again and the journal has loaded (2 seconds at most), the lock screen stays up with only its wordmark (`LockScreen(isHeld:)`), so the logo is held where it was typed and the "me" mark doesn't flash up like a second splash. The wordmark has two speeds (`Wordmark.Pace`): quick where the app waits on it (the splash), unhurried where nothing does (Today's, tapped).

**On device only.** Hashtag suggestions, "Reflection" (the on-device version of the web's AI reflection) with its follow-up chat (`ReflectionChat`: one session kept for the conversation, replies streamed, restarted with the last few turns when the context window fills, never saved; "Sum Up & Add to Entry" then adds the question that was asked, reworded to stand alone, as a bold line, and the writer's answers under it, tidied but not interpreted: `JournalIntelligence.chatSummary`, which is given the reflection's own closing question since the chat doesn't hold it) and Today's "Prompt from My Recent Entries" use Apple Intelligence's on-device model (`FoundationModels`, iOS 26+, hidden where unavailable). Prompts made from entry text use the `permissiveContentTransformations` guardrails: the default ones refuse ordinary hard journal entries (a fight, a rough night with the kids). To check one that's refused, run `reflectsOnAHardEntry()` with `TEST_RUNNER_DABBLE_REFLECT_FILE` pointing at its text (keep it out of the repo). Reminders (scheduled on the device, from `/api/v1/reminders`), the Face ID lock and drafts are local too.

**Entry template.** Settings → Entry Template (`EntryTemplate`, `EntryTemplateView`) keeps one template on the device, written and formatted like an entry and kept as typed (`RichText.typedRuns`: its blank lines and empty list items are where the writing goes; a draft keeps them too, a saved entry drops them). With "Start New Entries with It" on, a new entry opens holding it (and can't be saved until something's written). Otherwise the composer's lightbulb row offers "Use Template" beside a prompt that's only written when tapped for; holding the lightbulb button adds the template either way. `-DabbleDebugTemplate "words"` sets one for a launch, for UI tests.

**Icons** are the Slab set (Font Awesome Pro, as on dabble.me), as template vector assets in `Assets.xcassets/Slab` (`slab-…`), sized 24pt. `appIcon(_:)` / `Label(_:icon:)` take a `slab-…` name or fall back to an SF Symbol for anything the set doesn't cover. `slab-sparkles` (on-device Apple Intelligence everywhere: Reflect, prompts, hashtag suggestions) and `slab-bolt` (Actions) are our own, drawn to match; `slab-claude` marks the Claude/ChatGPT connector. A selected tab shows its `-full` icon.

**Shake** the phone for a random memory: a preview sheet (Another / Open) over whatever you're reading. Not while typing, where shaking is iOS's Undo.

**Account settings.** The entry template, "Start New Entries with It" and Settings → Home Screen Widget's choice are kept on the phone (the composer and the widget read them there, offline too) and on the account (`AccountSettings`, `/api/v1/app_settings`), so Sign Out, which clears the phone's copy, a reinstall or a new phone doesn't lose them. A change made on the phone is pending until the server has it (a failed send goes again on the next refresh); otherwise each refresh takes the account's copy, and anything the account has never had is sent up from the phone. The phone's copy belongs to one account (`accountSettings.account`): a different account signing in starts from its own. Each widget's own Edit Widget choice stays on the phone.

**Rewind** ("2026 Rewind", PRO): a year in review, offered as a card at the top of Stats from November through January (January looks back on the year just ended) once that year has five entries; before that the card says how many more it takes. It opens full screen as a run of cards tapped through like a story (`RewindView`). `Rewind.build` works the year out on the device from its entries (`/api/v1/entries?year=`): counts, the biggest month, the longest gap, the people and places named (Apple's NaturalLanguage name recognition, or names by their capitals where that isn't available), songs, hashtags, dated-tag milestones and photos. With Apple Intelligence on, `JournalIntelligence.rewindStory` adds a sentence for the biggest month, a phrase for each person named most, the line of the year (picked by number from the writer's own sentences, never written) and the year in a few words; each is checked against the entries and left out if it doesn't hold up, and the result is kept on the device until the year's entries change. Nothing leaves the device. Photos carry most cards: prints from the month, from the days a person or place was named, from the day of a song or of the line of the year, and every photo at the end. `-DabbleDebugRewindYear 2026` shows it out of season, and `-DabbleDebugRewindPhotos YES` gives entries stand-in photos from the development server.

**Stats** (Journal > Stats, PRO): the whole journal's totals in four tiles that each go somewhere (the Journal, Photos, the streak's year, the hashtags), then one year at a time under a year menu: the day grid, entries per month, the year's hashtags (`GET /api/v1/stats/days?year=`) and a prompt for an AI connector. Holding a day in the grid previews its entry with Open, or says nothing's written and offers Write Entry (`dayPreview`).

**An open entry** (`EntryDetailView`) has no card: it's on the page's own background (white in light mode) from the bar down to its last line or its photo, which runs edge to edge. When On This Day follows (`SameDaySection`), the entry ends in a soft line and On This Day is on the Paper color: the same date in other years, a tap opening one over it and a hold previewing it. The swipe left for Actions starts on the entry only. From a list, the Actions sheet starts with Open (the entry in full). A floating group at the bottom's middle (over the song player) holds the entry before, Reflect (where Apple Intelligence is on) and the entry after; it steps aside while a long entry is scrolled down and is back on the way up, at the entry's foot and at the page's. A pull down still reflects, and a swipe on the title's date still steps between entries. The title is the entry's date at the top of the page and how long ago that was once it's scrolled down (a tap switches it too); On This Day's headings say how long ago each was from now ("November 2021 • 5 years ago"). Once an entry has been opened from another's On This Day, the back arrow held lists everywhere to go back to (each entry behind it, then Today, the Journal or Search), handed down as `backTrail`; a tap still goes back one.

**Working on it** is three dots that rise one after another, like typing (`TypingDots`), in place of iOS's spinner wherever something's being written, refreshed or uploaded: a prompt or reflection being generated, hashtags being suggested, a photo processing or uploading, and every pull to refresh (`refreshDots()` beside `.refreshable`; iOS's own refresh spinner is kept clear in `DabbleMeApp`). Pages that are simply loading keep iOS's spinner.

**The composer's lightbulb** (what to write about, on every plan) opens a row with a question to answer, where there's one to be had, over what was on the phone's calendar on the entry's day (`CalendarRow`, `DayCalendar`, EventKit), the two scrolling as one section with one heading ("A prompt for you / Agenda" when the day has events) and the question's place held at three lines so the events under it don't move as it's written; a tap puts an event in the entry as a heading, where the cursor is: on its line when that's empty, otherwise right under the line it's on, with the cursor left on a fresh line below (`addQuestion`; the question does the same). A day with no events shows nothing of the calendar; "On your calendar" heads only the line that says the calendar isn't allowed. Settings → Calendars (`CalendarSettingsView`) chooses which calendars count: all but subscribed ones to begin with (iOS doesn't tell an app which are ticked in the Calendar app). Accounts are added and removed in iOS's Settings (Apps → Calendar → Calendar Accounts), which the page says; there's no link an app may open to it. It's read on the device when the row's opened (iOS asks the first time) and nothing of it is sent anywhere unless it's tapped in. `-DabbleDebugCalendar YES` shows a made-up day. For UI tests that open the row without it, give the simulator calendar access once (`xcrun simctl privacy <device> grant calendar me.dabble.ios`), or iOS's own question covers the app. Holding the hashtag button tags the entry's own words with the writer's hashtags they match. Typing a "#" and a letter brings up the writer's hashtags that start that way, in a row of their own that takes the place of whichever row was open and goes when the hashtag's finished (`RichTextEditorModel.typedHashtag`, `hashtagCompletions`); a tap completes it, keeping the letters already typed as they were typed (auto tagging keeps the writer's capitals too: it puts the "#" before the word as written). A "#" and a number isn't taken for one.

**Calendars** are iOS's own month view with a dot under each written day (`WrittenDaysCalendar`, a `UICalendarView`), from the first entry's day to today. Jump to a Day (`DayPickerSheet`: from the timeline scrubber, the Journal's "me" mark held, Search, or an open entry's date held) opens a written day's entry in full and opens the composer on a day without one; the round button with today's date in its header turns the calendar back to this month. The composer's date is the same calendar in a popover under it.

**Chrome.** Pushed pages use the Slab left arrow (`slabBackButton()`), and rows that open a page end in the Slab right arrow (`PaneLink`). Round buttons over a photo (the viewer's X) share the dark translucent backing of its Save and Share (`RoundButtonBacking`).

**Songs** (Journal > Songs; `PlaylistView`) lists the entries with a Spotify song: a short preview and the songs. A song plays in Spotify's own embedded player (`SpotifyPlayer`, its iFrame API in a web view) docked at the bottom: a preview, or the whole song for someone signed in to Spotify there. The player swipes like a list row: left for Open in Spotify and an X that puts it away (keep swiping and it goes), right, under an entry, for the Playlist. An open entry with a song has the same player under it (`SongPlayerBar`), once one of its songs is tapped, one song at a time. Nothing is requested from Spotify until a song is played, there or on the Playlist. A Playlist row has the entry's photo as a small square at its right (`EntryThumbnail`, as On This Day under an entry).

**Daily reminder** (`ReminderScheduler`): one local notification a day with an entry to look back on, skipped once the day is written. Settings → Reminders is three rows, each to a page: Push and Email, then the widget's page and Past Entry Filters. Each of the three says there's something to look back on, and has its own switch for showing the entry itself, on its own page (Push: Show Past Entry, kept on the device; Email: Show Past Entry, the account's, since an email keeps its copy in an inbox; the widget: Show Entry Previews): off, it's how many there are ("You have 3 entries from this day in past years."). Past Entry Filters is what all three share (PRO: the words that leave entries out, and whether to go back over a year). Push holds (on or off, the time, which starts as the daily email's hour, and the days; kept on the device); Email, its days, hour and time zone. With a past entry the notification is that entry ("Rewind · 22 days ago", the start of it and its photo; iOS's own Show Previews setting for the app hides both on a locked phone); without one, "How was your day?". A tap opens Today, whatever time it's set for. Touch and hold offers Read the Memory and New Entry. They're scheduled two weeks ahead on the device and rebuilt whenever the app opens or an entry is written in it, and now and then in the background (`BackgroundRefresh`, when iOS allows), so an entry written by email can still be the one a later day looks back on.

**Photos** are re-encoded on the device to a JPEG of at most 2400px, with all metadata removed (including GPS) before upload. The server then processes them the same way as MCP uploads (`ProcessEntryImageJob`).

## Tests

```bash
xcodebuild -project DabbleMe.xcodeproj -scheme DabbleMe -destination 'platform=iOS Simulator,name=iPhone 17' test
```

The tests cover PKCE, day handling across time zones, JSON decoding, rich text layout, round-trips and list indents, GPS stripping, the widget's day and year rollover, and reading hashtags from model replies. API behavior is covered by `spec/requests/api_v1_spec.rb` on the Rails side.

### UI tests against a local server

The UI tests that need a server skip unless you pass a token from `bundle exec rails ios:demo_account`:

```bash
TEST_RUNNER_DABBLE_TOKEN=<token> xcodebuild test -project DabbleMe.xcodeproj -scheme DabbleMe \
  -destination 'platform=iOS Simulator,name=iPhone 18 Pro' -only-testing:DabbleMeUITests
```

- They talk to `http://localhost:3000`. If something else on the Mac has taken that port on localhost (an editor's port forwarding answers 403), point them at the Mac's own address: `TEST_RUNNER_DABBLE_SERVER=http://$(ipconfig getifaddr en0):3000`.
- Start Puma before Sidekiq, a few seconds apart: `.env` is a 1Password pipe, and two processes opening it at once can leave one without AWS keys.
- **Face ID lock test:** enroll Face ID on the simulator (`xcrun simctl spawn <device> notifyutil -s com.apple.BiometricKit.enrollmentChanged 1` and then `-p` the same name). Run a helper that sends one match (`xcrun simctl spawn <device> notifyutil -p com.apple.BiometricKit_Sim.pearl.match`) whenever `$TEST_RUNNER_DABBLE_DEBUG_DIR/faceid-match` appears, then deletes the file. Also set `TEST_RUNNER_DABBLE_FACE_ID=1`.
- **App Store screenshots:** set `TEST_RUNNER_DABBLE_SCREENSHOT_DIR` and run `ScreenshotTests` on the iPhone 18 Pro (1206 × 2622) and iPad Pro 13" simulators. Reset the demo account first so Today has no entry yet, and set each simulator's status bar (`xcrun simctl status_bar <device> override --time 9:41 --batteryState discharging --batteryLevel 100 --wifiBars 3 --cellularBars 4`) and appearance (`xcrun simctl ui <device> appearance light`). It writes ten, `01-today` to `10-search`; copy them into `AppStore/Screenshots/` and run `Header and Search Results/source/render.sh` for the two wide images.
